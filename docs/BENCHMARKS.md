# FlowKit benchmarks

> Generated by `npm run benchmark` on 2026-11-22 with flowkit-mcp 0.3.1. Re-run it to reproduce these numbers on your machine; raw data is in [`benchmarks/results/latest.json`](../benchmarks/results/latest.json).

## Summary

| Question | Answer |
| --- | --- |
| How many tokens does one FlowKit call save? | **406 tokens per task on average (80% fewer)** across 13 common tasks |
| Multi-step workflows? | **65.4–77% fewer tokens**, even when the baseline writes one combined script |
| What does loading the tools cost? | **6,068 tokens once** for all 46 tools, about **1,668** for one tool group (`--tools`) |
| When does it pay off? | After **15 tasks** with all tools, **4–6 tasks** with one group |
| A 30-task session? | 15,219 tokens with own scripts → **9,107** (all tools) or **4,707** (one group) |
| Large outputs? | Converted text is returned as a bounded preview: **98.7% fewer tokens** than reading the file; **7.7 MiB** of binary output never enters the context |
| Do all tools work? | **46 of 47 tool runs passed**, 1 skipped (optional engine missing); median 465 ms per call |
| Are unsafe inputs rejected? | **6/6 boundary checks blocked** (path escapes, absolute paths, bad options, unknown arguments, missing files, wrong types) |

Token counts are estimated as UTF-8 bytes ÷ 4. They are a transparent approximation, not provider billing data; use your model host's usage fields for exact billed tokens.

## 1. Tokens per task

Each task compares what the agent sends and reads:

- **Own script:** the request, a compact but safe Node.js script sent through a shell tool, and the script's output. Scripts validate workspace paths and file sizes, avoid the shell, set timeouts, and refuse to overwrite files — the same guarantees FlowKit provides. They are 25–37 lines long.
- **FlowKit MCP:** the request, one tool call, and FlowKit's JSON result.

![Tokens per task: own script vs FlowKit MCP](benchmarks/tokens-per-task.svg)

| Task | Tool | Own script | FlowKit MCP | Saved | Reduction |
| --- | ---: | ---: | ---: | ---: | ---: |
| DOCX → Markdown (with preview) | `document_to_markdown` | 661 | 330 | 331 | 50.1% |
| Markdown → PDF | `document_to_pdf` | 366 | 60 | 306 | 83.6% |
| Merge 3 PDFs | `pdf_merge` | 455 | 78 | 377 | 82.9% |
| Extract PDF pages 2-4,7 | `pdf_extract` | 429 | 74 | 355 | 82.8% |
| Halve a scanned PDF's size | `pdf_reduce` | 634 | 119 | 515 | 81.2% |
| Encrypt a PDF (AES-256) | `pdf_encrypt` | 445 | 84 | 361 | 81.1% |
| Resize image to fit 800×800 | `image_resize` | 514 | 76 | 438 | 85.2% |
| PNG → JPEG at quality 85 | `image_convert` | 459 | 77 | 382 | 83.2% |
| Trim audio 0:30 for 45 s | `audio_trim` | 531 | 83 | 448 | 84.4% |
| Normalize loudness to −16 LUFS | `audio_normalize` | 568 | 73 | 495 | 87.1% |

DOCX → Markdown saves the least because both sides return a 1,000-character preview, which dominates the payload.

## 6. Output kept out of the context

FlowKit writes artifacts to disk and returns metadata. Text conversions return at most a 1,000-character preview; the agent reads more with `flowkit_read_text` only when it needs to. Measured on a 13.3 KiB Markdown conversion of a 36-section report:

![Text output kept out of context](benchmarks/context.svg)

| Tool | Output size | Tokens to read the output | FlowKit result tokens |
| --- | ---: | ---: | ---: |
| `document_to_markdown` | 13.3 KiB | 3,394 | 309 |
| `document_to_html` | 29.1 KiB | 7,458 | 33 |
| `document_to_text` | 21.6 KiB | 5,535 | 33 |
| `document_to_latex` | 39.5 KiB | 10,105 | 35 |
| `document_to_rst` | 26.1 KiB | 6,672 | 33 |

Binary outputs (images, audio, video, PDF, Office files) are never base64-encoded into results: 7.7 MiB of artifacts in this run were returned as paths and metadata only.

## 8. Safety boundary checks

| Check | Tool | Blocked | Server response |
| --- | ---: | ---: | ---: |
| Path escape (../) | `read_text` | ✅ yes | Path must stay inside the configured workspace |
| Absolute path | `file_metadata` | ✅ yes | Use a relative workspace path |
| Out-of-range option | `image_resize` | ✅ yes | Input validation error: Invalid arguments for tool flowkit_image_resize: width: Too small: expected number to be >=1 |
| Unknown argument | `pdf_reverse` | ✅ yes | Input validation error: Invalid arguments for tool flowkit_pdf_reverse: Unrecognized key: "shell" |
| Missing file | `document_to_markdown` | ✅ yes | File or directory is missing or inaccessible in the workspace |
| Wrong file type | `read_text` | ✅ yes | Read text accepts Markdown or TXT; convert other documents first |

## Methodology and limitations

- UTF-8 bytes / 4 (a transparent approximation, not provider billing data)
- Request + a compact, safe Node.js script sent through a shell tool + its stdout. Scripts validate workspace paths and sizes, avoid the shell, set timeouts, and refuse to overwrite.
- Request + FlowKit tool call(s) + FlowKit's JSON result(s), plus the once-per-session tool list and server instructions.
- Baseline writes one combined script for the whole workflow; MCP makes one call per step.
- A retry adds a failed first attempt: the broken script and its error output (baseline) or the rejected call and its validation error (MCP). Session totals with retries assume 25% of tasks need one.
- Clients that load tool schemas on demand pay little of the fixed cost; the all-tools figures are the worst case.
- Scenario scripts and results are in [`benchmarks/lib/scenarios.mjs`](../benchmarks/lib/scenarios.mjs). Tool definitions are read from the live server, so they always match the current code.
- Execution times depend on hardware and engine versions; compare runs on the same machine.
- The baseline assumes the model writes a correct, safe script. Real agents often skip safety checks (shorter but riskier) or need several attempts (longer).
